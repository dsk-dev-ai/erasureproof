# Deploy on Render

This is the fastest public demo profile. It runs the API and console in one
Docker service, uses a free managed PostgreSQL database, and enables anonymous
sandbox onboarding.

## What the free profile does and does not do

- One container serves the React console at `/console`, the API under `/v1`,
  OpenAPI at `/docs`, and the health probes.
- PostgreSQL stores tenants, requests, identities, API keys, approvals, and audit
  events.
- The container filesystem stores evidence snapshots, the ledger, attestations,
  and sandbox source files. **Render free web services have no persistent disk**,
  so those artifacts disappear on deploy, restart, or host migration. Database
  rows survive, but evidence references, ledger continuity, and attestation
  verification can break. `ERASUREPROOF_DATA_DIR=/data` only helps when `/data`
  is backed by a persistent disk.
- The free PostgreSQL instance is temporary and expires after its 30-day window.
  This instance expires on **2026-11-27**. Upgrade or migrate before then.
- Anonymous sandbox creation is limited to 3 per IP per day and 100 globally per
  day. Keys expire after 7 days.

## What survives a free-tier restart

| Artifact | Free-tier behavior |
| --- | --- |
| Tenants, requests, identities, API keys, approvals, audit events | Stored in PostgreSQL; survive web restarts until the database expires |
| Evidence snapshots under `ERASUREPROOF_DATA_DIR/evidence` | Lost on deploy, restart, or host migration |
| Ledger at `ERASUREPROOF_DATA_DIR/ledger.jsonl` | Lost; hash-chain continuity is broken |
| Attestations under `ERASUREPROOF_DATA_DIR/attestations` | Lost; previously issued signatures can no longer be served |
| Sandbox connector files | Lost with the container |

A health check can still return `200` after an artifact reset because the API is
running and PostgreSQL is connected. Treat missing evidence, a broken ledger, or
failed attestation verification as data-integrity failures, not as a healthy
free-tier quirk.

## Migrate before 2026-11-27

1. Create a paid or external PostgreSQL database with automated backups.
2. Dump the Render database with `pg_dump` and restore it into the new database.
3. Point `ERASUREPROOF_DATABASE_URL` at the new database and redeploy.
4. Attach a persistent disk or shared volume to `/data`, or configure durable
   storage for evidence, ledger, and attestations.
5. Run `erasureproof ledger verify`, download sample evidence, and verify an
   existing attestation before deleting the old database.
6. Keep the old database read-only for a short rollback window, then remove it.

Install a persistent disk before collecting any evidence you intend to keep.
Without one, every deploy can erase the artifacts while PostgreSQL still holds
rows that point at them.

## Option A: deploy the repository with a Blueprint

1. Push the repository to GitHub.
2. In Render, choose **New → Blueprint** and select the repository.
3. Render reads `render.yaml`, creates `erasureproof-db`, and prompts for
   `ERASUREPROOF_API_KEYS` because it is marked `sync: false`.
4. Enter a JSON array containing one bootstrap administrator key:

   ```json
   [{"key":"replace-with-a-long-random-value","role":"admin","tenant_id":"*","subject":"bootstrap-admin"}]
   ```

   Generate the key locally with `openssl rand -hex 32`. Never reuse a demo key.
5. Apply the Blueprint and wait for `/healthz` to pass.
6. Open `https://<service>.onrender.com/console`.

`ERASUREPROOF_ATTESTATION_KEY` is generated by Render. The database connection
string is injected automatically and normalized to the Psycopg driver.

## Option B: deploy the Docker image manually

Create a PostgreSQL instance, then a **Web Service** with:

| Setting | Value |
|---|---|
| Environment | Docker |
| Region | Oregon (or nearest) |
| Plan | Free |
| Health check path | `/healthz` |
| Dockerfile | `Dockerfile` at repository root |

Environment variables:

```text
ERASUREPROOF_ENVIRONMENT=production
ERASUREPROOF_AUTH_MODE=api_key
ERASUREPROOF_DATABASE_URL=<internal PostgreSQL connection string>
ERASUREPROOF_DATA_DIR=/data
ERASUREPROOF_POLICY_DIR=/app/policies
ERASUREPROOF_WEB_DIR=/app/web/dist
ERASUREPROOF_ATTESTATION_KEY=<openssl rand -hex 32>
ERASUREPROOF_API_KEYS=[{"key":"<long random bootstrap key>","role":"admin","tenant_id":"*","subject":"bootstrap-admin"}]
ERASUREPROOF_DEMO_ENABLED=false
ERASUREPROOF_SELF_SERVE_ENABLED=true
ERASUREPROOF_SANDBOX_TTL_HOURS=168
ERASUREPROOF_SANDBOX_DAILY_LIMIT=100
ERASUREPROOF_SANDBOX_PER_IP_DAILY_LIMIT=3
ERASUREPROOF_REQUIRE_REMEDIATION_APPROVAL=false
ERASUREPROOF_RATE_LIMIT_PER_MINUTE=300
ERASUREPROOF_TRUST_PROXY_HEADERS=true
ERASUREPROOF_HSTS_SECONDS=31536000
ERASUREPROOF_EXPOSURE_ENABLED=false
```

Do not set `ERASUREPROOF_AUTH_MODE=disabled` or leave the default attestation key
in production. Startup validation rejects both. The Docker command honors
Render's `$PORT`.

## Verify the deployment

```bash
curl -s https://<service>.onrender.com/healthz
curl -s https://<service>.onrender.com/readyz
curl -s https://<service>.onrender.com/version

SANDBOX=$(curl -s -X POST https://<service>.onrender.com/v1/onboarding/sandbox \
  -H 'content-type: application/json' \
  -d '{"workspace_name":"Deploy check"}')
echo "$SANDBOX" | python3 -c 'import json,sys; print(json.load(sys.stdin)["sample_request_id"])'
```

Then open the console from the generated link, paste the sandbox key into
Settings → API access, and run the seeded request. Attestations should be
available immediately, and the API keys page should show the sandbox key with a
revoke action.

## Rotate or recover

- If the bootstrap key leaks, create a scoped admin key first, add it to
  `ERASUREPROOF_API_KEYS`, deploy, then remove the old entry. Static keys are only
  read from the environment.
- Database-backed tenant keys can be rotated and revoked from the console or
  `POST /v1/api-keys/{id}/rotate`.
- Changing `ERASUREPROOF_ATTESTATION_KEY` invalidates verification of existing
  attestations and backups. Keep old keys for verification if you rotate them.

## Cost controls

- Free services sleep after inactivity; the first request wakes them.
- Set the sandbox global daily limit lower if you expect traffic spikes.
- Keep exposure scanning disabled unless you have a commercial search provider.
- Move to paid PostgreSQL and durable storage before onboarding real customers.
